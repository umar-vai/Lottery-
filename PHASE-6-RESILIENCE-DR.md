# Phase 6 — Resilience, Disaster Recovery & Backup Readiness

Date: 2026-10-07

## Scope

Phase 6 hardens the remaining privileged credit-review boundary, revalidates logical disaster recovery, adds a Support Points recovery drill, documents the actual infrastructure that must be reconstructed after a database restore, and introduces an operator-safe logical backup workflow for the current Free-plan Supabase project.

## 1. Current backup reality

The Supabase organization for `Lottery DRAW01` is currently on the **Free plan**.

Current Supabase documentation states:

- automatic daily database backups are provided on Pro, Team, and Enterprise plans;
- Free-plan projects should create regular logical exports with `supabase db dump`;
- database backups do **not** contain the actual Storage API objects;
- a database restore alone does not recreate Edge Functions, Auth provider configuration, project API keys, or other project-level infrastructure.

Therefore the current production recovery plan must include an off-site logical database export until the project is upgraded to a plan with managed backups/PITR.

### Operator backup helper

Use:

`scripts/export-offsite-backup.sh`

The script:

- requires `SUPABASE_DB_URL` from Dashboard > Connect;
- writes outside the Git repository by default;
- creates separate `roles.sql`, `schema.sql`, and `data.sql` exports;
- uses the current Supabase CLI backup pattern;
- refuses an obvious repository-local backup destination;
- uses restrictive file permissions;
- generates a manifest and SHA-256 checksums;
- explicitly marks Storage objects / Edge Functions / Auth provider configuration as outside the database dump.

**Never commit a production data dump to this public repository.**

A real off-site backup file is not generated by this phase because the connected management surface does not expose the database password and this repository is public. The operator must run the helper with a private database connection string and copy the resulting directory to encrypted off-site storage.

## 6. Full restore / PITR status

A real full restore is not performed against production as a drill.

The organization is Free-plan, so managed daily backups/PITR are not currently the recovery control.

A Supabase development branch currently reports a cost of **$0.01344/hour** and also does not automatically copy production data. Creating a paid branch therefore would not by itself prove production-data restore.

A true restore rehearsal needs:

1. a private logical backup produced with the backup helper;
2. a separate destination database/project;
3. explicit cost approval for that destination if billable;
4. restore of roles -> schema -> data;
5. separate restoration/reconfiguration of Storage objects, Edge Functions, Auth providers, API keys, and project settings;
6. cron/outbound job inspection before enabling live behavior;
7. Phase 1–6 database/runtime verification after restore.

## 8. Incident response procedure

1. Record incident start time, affected user/event/transaction IDs, and suspected write path.
2. Disable only the damaging write path if possible.
3. Capture current affected-row snapshots before repair.
4. Obtain known-good values from an off-site dump, audit evidence, or managed backup/PITR if available.
5. Restore in dependency order.
6. Run Draw Credit integrity.
7. Run the Phase 2 lottery DR drill.
8. Run the Phase 6 Support DR drill when Support data is involved.
9. Run Phase 1–6 static/runtime security contracts.
10. Verify cron health and Operations Incident Center.
11. Verify Edge/Storage/Auth infrastructure separately.
12. Re-enable writes only after all invariants pass.
